# 开发电脑的编译缓存怎么管理

这是从源码编译时的电脑空间问题。普通用户下载镜像或安装软件升级包，不会在
电脑上生成整套 Rust 编译缓存。

Cargo 把最终程序与中间文件放在 target/build 目录。中间文件能加快下一次编译，
但不需要随程序交付。目前 Cargo 的自动回收主要覆盖下载的全局缓存，不能用它
代替 target 构建目录管理。详见 [Cargo 构建缓存](https://doc.rust-lang.org/cargo/reference/build-cache.html)
和 [Cargo 缓存配置](https://doc.rust-lang.org/cargo/reference/config.html#cache)。

## 项目保留规则

1. 日常开发固定使用主机与 ARM 两组缓存，不为每个提交长期保留一整套 target。
   通过项目构建命令设置 `CARGO_TARGET_DIR`，不修改其他项目的全局 Cargo 配置。
2. 独立可复现验证仍用两套隔离的临时 target。验证通过后，把二进制、源码版本、
   哈希及测试记录放到独立发行目录，再清掉临时对象、增量、Zig 和临时文件缓存。
3. 日常两组缓存各按 20 GiB、合计 40 GiB 预算检查；超过预算或任一相关盘空闲
   低于 20 GiB 时，先停止新构建并列出可回收内容。预算是本项目的维护规则，
   不代表 Cargo 会自行执行。空闲的旧缓存允许整套重建，不能靠持续换盘躲过空间检查。
4. 已发布软件、回退包、签名资料、原始模型、用户标定和固定验证基线不属于缓存。
   镜像制作中的临时展开目录也要与正式镜像分开，验收后按清单清理。
5. 清理前检查当前构建锁、进程引用、挂载点和实际绝对路径；源码目录、链接指向、
   未识别目录和活动缓存均不自动删除。旧目录里仍有工具依赖的程序，应先保留
   或单独归档并核对哈希。

## 手动清理自己的 Cargo 项目

在确认空闲的项目里，可使用 Cargo 自己的清理命令。若指定了共享 target，
必须明确核对它还被哪些构建使用；清理会使后续编译重新生成中间文件。

```sh
cargo clean --manifest-path /你的源码/Cargo.toml --target-dir /你的专用构建缓存
```

短期验证可以使用 `CARGO_INCREMENTAL=0`，减少只编译一次时的增量占用；日常
开发保留有预算的一组增量缓存即可。发行包不应携带 target、构建临时目录或
维护者个人文件。

## WSL 还需要检查宿主盘

Linux 内部删除文件后，要分别检查 Linux 可用空间和 Windows 的实际盘符空间。
虚拟磁盘文件可能仍然很大。回收宿主空间是另一项维护，不能直接删除 ext4.vhdx。

回收前检查本机 `wsl --version` 和 `wsl --help`。例如本次使用的 WSL 3.0.3
`--manage <发行版> --compact` 会停止目标发行版，并执行带自动修复的离线检查；
不适合作为每次构建后无提示运行的命令。应先结束活动任务、确认维护范围，再
比较虚拟盘大小与宿主余量，并复验关键文件。参见 [Microsoft 磁盘管理说明](https://learn.microsoft.com/en-us/windows/wsl/disk-space)
和 [本机 WSL 版本的离线检查实现](https://github.com/microsoft/WSL/blob/15ea3b3846c5f18318722d1381186b2ff6ed72eb/src/linux/init/main.cpp#L2986)。

本轮软件升级继续使用现有27日版的升级入口，无需为每次功能更新重新制作镜像。
